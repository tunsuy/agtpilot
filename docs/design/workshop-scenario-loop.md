# 工坊场景运营循环——从单发模板到档案驱动的运营台 (Scenario Loop)

- 日期: 2026-10-10
- 状态: **设计提案**(未动代码,排期待定)
- 前置阅读: `ARCHITECTURE.md`(微内核 / 契约)、`apps/web/src/components/workshops/registry.ts`(现有工坊注册表契约)
- 背景对齐: 工坊已与连接器解耦(d3552a8),本文是解耦之后的下一步——工坊从「Prompt 生成器」升级为「有档案、有循环的运营实体」

## 1. 背景与动机

### 1.1 现状:工坊是无状态的单发按钮

当前链路(`WorkshopsView.tsx` → `page.tsx:969` `onRunPrompt` → `handleRun` → 新建 Mission → 跳驾驶舱):

```
表单选风格 → buildXhsPrompt 拼 Prompt → 单次 Mission → 看执行流 → 结束
```

对「帮我翻译一段话」这类单次任务够用。但对高频场景用户——本文的锚定画像是**用 agtpilot 运营小红书的普通博主(她)**——缺三样东西:

| 缺失 | 表现 | 后果 |
|---|---|---|
| **记忆** | 每次运行都要重新选风格;Agent 不知道她的赛道、人设、语气 | 输出不一致,每次都是「匿名工具」 |
| **节奏** | 运营是周循环(选题→成稿→发布→复盘→迭代),工坊只有「单发按钮」 | 高频用户在为低频结构付导航与重复成本 |
| **闭环** | 发布后数据回不来,Agent 不知道上一篇爆没爆 | 选题建议永远盲猜 |

对照她真实的一周:**周一**要 7 个选题(最好基于上周数据)、**周三**挑 3 个成稿、**发布**注定手动(小红书个人号无发布 API)、**周末**想有人帮她归因「为什么这篇爆了」。现状只覆盖了「周三」。

### 1.2 设计原则(全文的总纲)

> **她只出判断,不出搬运。**

她在循环中不可替代的动作只有三类:选哪个题、改哪句话、发不发。抄写、转录、格式转换——所有「搬运」都必须消灭。由此推论:

- 账号档案 = 消灭「每次重新解释自己是谁」的搬运(P0)
- 结构化交付物 + 一键复制 = 消灭「逐字段转录成发布格式」的搬运(P0)
- 截图读数 = 消灭「抄数据」的搬运(P1)
- 发布到草稿(托管模式) = 消灭「复制粘贴发布」的搬运(P2,opt-in)
- 自适应落地页 = 消灭「在 8 张卡片里找那张卡」的导航搬运(伴随)

每一步的形态都是:**把人的输入从文本转录降级成动作**。

## 2. 核心抽象:场景档案 (ScenarioProfile)

工坊的所有场景共用同一套结构,小红书是第一个实例:

```
场景档案(每用户 × 每场景一份,服务端实体)
├─ 定位: 赛道 / 目标人群 / 差异点
├─ 人设: 语气样例(她自己写的两行文案) / 禁忌(不要感叹号、不提价格…)
├─ 节奏: 发布频率 / 内容配比(如教程:种草:日常 = 4:3:3)
└─ 认知(可被复盘写回): 已验证的爆款归因,如「封面带价格数字的笔记数据稳定更好」
```

- **这是通用抽象,不是小红书专用**:投研场景的档案是「关注池 + 风险偏好」,教研场景是「学科 + 学情 + 出题偏好」。档案、周复盘、闭环这套结构对哪个工坊都是同一套。
- **存储必须是服务端**(类似 Mission 的 per-user 实体)。现状 `history.ts` 用 localStorage(`agtpilot.workshop.history.v1`,最多 20 条)——历史可以留在本地,档案必须跟账号走,否则换设备即失忆。
- **注入点**:`buildWorkshopRun(id, params)`(`run.ts` L25-122)在各构建器里自动拼接档案段落,表单不再询问档案已回答的问题。

### 2.1 数据契约草案

```ts
// 档案:服务端实体,按 (userId, scenarioKey) 唯一
interface ScenarioProfile {
  scenarioKey: string;            // 'xhs' | 'invest' | 'edu' | ...
  version: number;                // 认知字段被复盘写回时递增
  positioning: { niche: string; audience: string; differentiation?: string };
  persona: { toneSamples: string[]; taboos: string[] };
  cadence: { postsPerWeek?: number; mix?: Array<{ kind: string; weight: number }> };
  insights: Array<{               // 复盘写回,只增不删(可标记失效)
    claim: string;                // 「封面带价格数字的数据更好」
    evidence: string;             // 归因依据(哪几篇、什么数据)
    at: number;
  }>;
}

// 注册表扩展:声明工坊依赖档案
interface WorkshopDef {
  // ...现有字段(registry.ts L41-52)不变
  profileSlot?: string;           // 对应 scenarioKey;有值 → 首次使用触发档案引导
  artifacts?: ArtifactSpec[];     // 结构化交付物声明(见 §3)
}
```

## 3. P0 · 结构化交付物:从「一段文本」到「字段级笔记包」

现状成稿是 Prompt 产出的自由文本。改为**按发布操作单元分字段**的 Artifact(复用 `ArtifactState`):

```
笔记包(小红书图文实例)
├─ 标题候选 ×5          (每条独立复制)
├─ 封面文案              (对应网页发布页的封面文字)
├─ 正文                  (含 emoji/换行,贴进发布框即成型)
├─ 标签                  (话题 tag 串)
├─ 发布建议              (建议时段 + 理由)
└─ 一键整卡复制          (按 标题→正文→标签 顺序排好,一次进剪贴板)
```

- 她的真实操作是「贴进小红书发布页」,字段顺序与发布页对齐,一次粘贴即成型。
- **Prompt 预览降级**:`WorkshopModalShell`(`forms/shared.tsx` L174-189)的「所见即所发」是开发者透明度设计,对目标用户是噪音——从默认展示改为折叠在「高级」区。
- 交付物由构建器的 Prompt 约定输出格式 + 前端解析渲染(格式即契约,评测时可校验)。

## 4. P1 · 循环的两半:多步工作流 + 数据回流

### 4.1 从「单发」到「选题→成稿→审」小工作流

一次运行拆成带人工确认点的多步 Mission(复用驾驶舱已有的 MissionStep + 审批机制,工坊侧只是把「一次表单提交」升级为「一个多步任务」):

```
选题步: Agent 出 7 个选题(附依据:档案认知 + 上周数据)
   ↓ 人工确认: 她勾选 3 条
成稿步: 批量产出 3 篇笔记包(Artifact)
   ↓ 人工确认: 逐条可改(改完进入待发布)
```

比让她自己跑两次、中间手动衔接体面得多;审批点天然落在「选哪个题、改哪句话」两个判断上——正符合 §1.2 原则。

### 4.2 数据回流:每周一张截图

- **主路径**:她从创作中心数据页**截一张图丢进对话**,视觉模型读赞藏评做周复盘——零打字、零格式处理,截图是她本来就会的动作。(依赖:mission 支持图片输入。)
- **升级路径**:`只读` 浏览器连接器,经授权后 Agent 自己读创作中心数据页——读不写,风险与发布完全不同量级。
- **产出**:周复盘报告 + **写回档案 `insights`**(「封面带价格数字的笔记数据稳定更好」)→ 下周选题自动带上已验证认知。**这一步把循环真正闭上,是与「AI 写小红书」类工具的差异化所在:别人只有生成,我们有反馈回路。**

## 5. P2 · 托管模式:发布到草稿(默认关闭)

### 5.1 事实基础(2026-10 核查,第三方来源,上线前须实测)

- 小红书 App 草稿箱一直有(「我的草稿」);
- 网页创作平台(creator.xiaohongshu.com)发布页**实时自动保存**为草稿(「已保存至草稿」提示),草稿箱在左侧菜单,资料称网页草稿同步至 App 草稿箱——**有旧资料称 App 草稿不能导入网页版,同步方向存在冲突,须实测**;
- 开放平台 API 的内容发布接口需商家/服务商资质,**个人号无官方发布/草稿 API**——「Agent 直调 API 存草稿」这条路不通。

### 5.2 形态

```
Agent 成稿
  → 浏览器连接器打开 creator.xiaohongshu.com/publish/imgNote
  → 上传封面图(≤9 张)、填标题/正文/标签
  → 什么都不按 —— 自动保存已在草稿箱        ← 永远停在这一步
  → 她打开 App,草稿箱里躺着 3 篇成稿,审一眼、调封面 → 发布
```

价值:最终判断权在她、且在她最舒服的地方(App 内审稿是既有习惯,封面细节只有她能判断);零复制粘贴;**发布动作从头到尾是她的**。

### 5.3 风险定性(为什么 opt-in、默认关)

- 浏览器自动化操作官方网页属于风控灰色地带,账号风险由她承担——**必须首次开启时明示**,并限频(如每日上限);
- 一键整卡复制(§3)仍是默认主路径,托管模式只服务愿意用自动化换便利的用户;
- 网页版**定时发布**可作进阶选项,但方向不得倒置:默认是草稿(发布需她主动按),定时发布是她显式选择后的例外——**安全默认不能是「到点自动发、取消窗口留给她」**。

### 5.4 上线前实测清单

1. 草稿同步方向:网页存草稿 → App 草稿箱是否出现(以及反向);
2. 自动保存触发条件:是否填入标题即存、无图纯文是否也存;
3. 图文 9 图上传、3:4 比例约束下的程序化传图;
4. 自动化操作的风控信号(同 IP/设备指纹连续操作的封禁案例调研)。

## 6. 自适应落地页:「我的台」+「全部工坊」

**模板一个不砍,首屏因人而异**(类比:支付宝首页只放高频应用,「全部应用」一页不少)。

```
打开工坊
├─ 有主场景(升格规则见下)→ 「我的」Tab 置顶:该场景运营台
│     (小红书实例:本周选题进度 / 待成稿 / 上周数据概览)
│     其余工坊:其余 Tab 与网格,一跳可达
└─ 无主场景 / 新用户 → 维持现状:分类 Tab + 8 卡网格
```

- **升格规则(简单起步,纯行为数据,不需用户声明)**:单一场景在最近使用中占比 >60% 且 ≥5 次 → 升格为「台」;数据源即 `history.ts` 的使用记录(现在只用于「最近使用」三张卡,`WorkshopsView.tsx:116` 已是雏形);
- 主场景可不止一个(邮件天天用 + 周报每周用 → 邮件是台、周报是卡);将来投研重度用户一样可以有投研台——「运营台」是每场景各配一台的通用机制;
- **机制上是「分区改 Tab」(d3552a8)方向的延续**:Tab 序列最前加「我的」(仅有主场景时出现),`全部` Tab 保持原样;
- **风险与兜底**:自适应首屏可能埋没轻度场景——兜底即「全部工坊」永远一跳可达,且升格可逆(占比跌破阈值自动降回卡片)。

## 7. 安全边界与红线

1. **Agent 永远不碰「发布」按钮**:发布是账号安全红线,自动发布的封号风险由用户承担,不值。托管模式的终点是草稿箱(P2),定时发布只能作为用户显式选择后的例外(§5.3);
2. **读写分级**:数据回流连接器只读创作中心数据页;写操作(填发布页)仅存在于 opt-in 托管模式,且开启时明示风控风险;
3. **档案是用户资产**:档案认知字段(`insights`)被 Agent 写回前须经周复盘报告的人工确认——写回的是「她认可的归因」,不是 Agent 的自说自话;
4. **审计**:托管模式每次网页操作落事件日志(填了哪篇、停在哪一步),事故可归因;
5. **Prompt 预览不删除只降级**:「所见即所发」的透明度设计对开发者/高级用户保留。

## 8. 实施路径 P0 / P1 / P2

| 阶段 | 内容 | 改动面 | 产出 |
|---|---|---|---|
| **P0** | ① 场景档案实体 + 小红书首次引导(3 分钟:定位/语气样例/节奏/禁忌)② 档案注入 `buildXhsPrompt` ③ 笔记包 Artifact + 一键整卡复制 + Prompt 预览降级 | `registry.ts` 加 `profileSlot`/`artifacts`;档案走服务端 per-user 存储(新 API 路由);`forms/` 表单简化 | 她的第二次使用明显好于第一次;发布操作从逐字段复制变一次粘贴 |
| **P1** | ① 选题→勾选→成稿多步工作流(复用 MissionStep 审批)② 截图读数周复盘 + insights 写回(经确认)③ 「我的台」自适应落地页(升格规则) | mission 多步任务发起路径;图片输入;`history.ts` 数据喂给升格判定 | 循环闭合:复盘影响下周选题;高频用户落地即运营台 |
| **P2** | ① 托管模式:浏览器连接器填网页发布页、停在自动保存草稿(opt-in、限频、审计)② 只读数据连接器 ③ 订阅节奏(每周一定时出选题,结果待审) | 浏览器连接器写路径 + 风险明示 UI;定时 Mission | 她的一周 = 看选题 → 勾 3 条 → 改两句 → 按发布 → 截一张图 |

依赖提示:P1 截图读数依赖 mission 图片输入能力;P2 托管模式依赖浏览器连接器体系成熟度——若 P1 的只读连接器先行验证了登录态保持与风控表现,P2 的写路径风险更可控。

## 9. 开放问题(待负责人拍板)

1. **档案存储位置**:服务端 per-user 实体挂现有 API 层(类似 Mission 的存取路径)还是进持久状态治理体系(`persistent-state-governance.md`)?档案含用户创作偏好,数据分级上应与记忆服务同档;
2. **多步工作流的发起形态**:工坊表单提交后是「一个多步 Mission」还是「Mission 序列」?与驾驶舱现有审批 UI 的映射需要原型验证;
3. **「我的台」升格阈值**:>60% 且 ≥5 次是拍的,是否需要按真实使用分布校准?冷启动期(总使用 <10 次)是否不启用升格以免误判?
4. **托管模式的合规口径**:浏览器自动化操作小红书网页版,产品上以什么口径告知风险?是否需要用户书面确认(而非弹窗勾选)?
5. **截图读数的模型路径**:视觉解析走哪个 provider、成本与准确率验收标准?
6. **优先级与既有提案的关系**:与 decision-model / cua 提案互不依赖可并行;若浏览器连接器排期受 cua 集成影响,P2 是否让位。
